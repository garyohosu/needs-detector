# AIに3,000円追加課金して「ニーズ検出器」を動かしたら、自分が一番困っている問題が見つかった

AIを使ってソフトを作ること自体は、もうそれほど珍しくありません。

仕様を書かせる。コードを書かせる。テストを作らせる。レビューさせる。うまく設計すれば、かなりの部分をAIに任せられます。

では、もう一歩進めて、**「何を作ればいいのか」までAIに考えさせることはできるのか**。

今回は、そのための実験として「needs-detector」というCLIツールを作りました。

名前の通り、顧客が本当に困っていることを見つけるための道具です。

ところが、完成までには少々問題がありました。

テストは通る。インストールもできる。CLIも起動する。

でも、肝心の「何を作ればいいのか」という結果が、いつまでたっても出てこなかったのです。

しかも私は途中で、AIサービスへ追加課金を3,000円ほど投入しています。

工具を作るために工具を作り、その工具を動かす仕組みまで作り始める。AI開発でよくある、なかなか立派な沼でした。

## AIに商品開発の初期工程を任せたい

needs-detectorの目的は、AIだけで「この商品は売れる」と断定することではありません。

むしろ逆です。

AIが勝手に作った物語と、現実に観察された事実を分けることを重視しています。

大まかな流れは次の4段階です。

1. 想定する利用者と課題仮説を描く
2. 現在使われている代替手段を調べる
3. 顧客インタビューの質問を作る
4. 実際の発言や行動から仮説を見直す

内部では、AIの推論、公開情報、引用、仮説、実際の顧客情報を区別して保存します。

また、実際のインタビューがない状態では、最終的な学習工程を止めるHuman Gateも入れました。

AIが勢いだけで「Customer Problem Fit達成です」と言い出さないためです。

## 44件のテストが通った。でも、それで何が分かったのか

開発は順調に見えました。

単体テスト、カバレッジ、wheelのパッケージング試験も通りました。Python 3.12のまっさらな環境へインストールし、リポジトリの外からCLIを起動する実験にも成功しました。

合成データを使ったデモも動きました。

Manual LLMの待機処理も動きました。

実インタビューなしで学習を止めるHuman Gateも正常でした。

つまり、ソフトウェアとしては動いています。

しかし、ここで私はようやく気づきました。

**動作確認の結果しか出ていない。**

「テストが何件通ったか」は分かります。

しかし、「どんな人が、何に困っていて、何を作る価値がありそうなのか」は何も分かりません。

これは、レストランの厨房設備を完璧に検査したのに、料理を一皿も出していないようなものです。

## さらにAutoLoopを動かし始める

そこで、実際の調査を行う指示を出しました。

ところが途中で、AIはAutoLoopという自動実行基盤をインストールし始めました。

今回やりたいのは、完成したneeds-detectorを使って結果を出すことです。

それなのに、結果を出すための自動化基盤を、さらに準備し始めたのです。

AIに目的を任せきると、こういうことが起こります。

「調査結果を作る」という本来の目的よりも、「立派な実行環境を作る」という手段の方へ進みやすい。

AutoLoopの導入を中断し、現在のCodexセッションから、needs-detectorを直接操作するように指示し直しました。

ここでようやく、実際のニーズ探索が始まりました。

## Claude Code、Codex、Gemini CLIのIssueを20件調べた

調査テーマは、私自身が最近かなり困っていた問題にしました。

> AIコーディングCLIを複数使う開発者は、利用量制限、コンテキスト喪失、再起動、複数AI間の引継ぎで何に困っているのか

調査対象は、次の公式GitHubリポジトリです。

- Claude Code
- OpenAI Codex
- Gemini CLI

公開Issueを20件収集し、単なる要望だけではなく、実際に作業が止まった事例、再実行した事例、履歴を探した事例、手動で引継ぎを作った事例を優先して整理しました。

もちろん、GitHub Issueは顧客インタビューではありません。

困った人が自発的に投稿した情報なので、利用者全体の何割が困っているかは分かりません。購入意思も市場規模も分かりません。

そのため、データ区分はすべて「unknown」としました。

それでも、現実に起きた出来事から、問題仮説の候補を作ることはできます。

## 出てきた優先ニーズ上位3件

needs-detectorによる分析では、次の3つが上位になりました。

### 1位：利用量制限や再起動をまたぐcheckpointと再開

AIコーディングCLIは、長時間動かしている途中で利用量制限に達したり、プロセスが停止したりすることがあります。

そのとき問題になるのは、単に会話履歴が消えることではありません。

- 何を目的に作業していたのか
- どこまで完了したのか
- 何を検証したのか
- どの成果物を信用してよいのか
- 次に何をする予定だったのか

これらが、再開可能な形で残らないことです。

利用者はログを探し、Git差分を確認し、同じ説明を別のAIへ入力し直します。場合によっては、同じ作業を最初から再実行します。

### 2位：長時間タスクの進捗と終了状態の可視化

AIが止まったとき、それが正常終了なのか、途中停止なのか、制限到達なのかが分からないという問題です。

「完了したように見えるが、実際には途中だった」という状態は厄介です。

人間は、どこまで確認済みなのか、何をやり直すべきなのかを判断できません。

### 3位：複数CLIや親子エージェント間のportable handoff

Claude CodeからCodexへ、CodexからGemini CLIへ、あるいは親エージェントから子エージェントへ作業を渡すとき、共通の引継ぎ形式がありません。

現在はMarkdownのメモ、会話の要約、Gitの差分、TODOファイルなどを、人間が組み合わせています。

しかし、要約だけでは重要な制約が落ちることがあります。Git差分だけでは、何を意図して変更したのか分かりません。

## 最有力の製品仮説は「Portable Work Checkpoint」

最も有望と判定された案は、**Portable Work Checkpoint**でした。

AIコーディング作業の途中状態を、特定のCLIに依存しない形式で保存する仕組みです。

例えば、次の情報を残します。

- 作業の目的
- 完了済みの作業
- 実行したテストと結果
- 変更した成果物
- 未完了の作業
- 判明している問題
- 次に行う操作
- 元のセッションやログへの参照

出力形式は、人間が読めるMarkdownと、別のAIが処理できるJSONの両方です。

これがあれば、Codexの利用量制限に達した後、Claude CodeやGemini CLIへ切り替えても、最初から説明をやり直さずに済むかもしれません。

実は、これは私自身が何度も経験している問題でした。

Claude Codeが5時間制限で止まる。

Codexが利用できなくなる。

別のAIへ渡すために、引継ぎ資料を作らせる。

複数のAIを動かすと、別のリポジトリや別の指示番号を処理し始める。

needs-detectorを動かした結果、自分が最も困っている問題が、最重要ニーズとして返ってきたわけです。

少々できすぎた話にも見えますが、調査対象を自分の問題に設定したので、当然といえば当然です。

重要なのは、自分の不満だけではなく、複数の公式リポジトリで似た問題が報告されていたことです。

## ただし、市場があるとはまだ言えない

ここは大事な点です。

今回分かったのは、問題が存在する可能性が高いということです。

しかし、次のことはまだ分かりません。

- どのくらいの頻度で発生するのか
- 1回あたり何分、何時間を失うのか
- 既存のresume機能で十分な人はどれくらいいるのか
- 個人開発者だけの問題なのか、チームでも起きるのか
- お金を払って解決したい問題なのか

つまり、製品仮説は出ましたが、Customer Problem Fitや市場成立は未確認です。

次は、実際にAIコーディングCLIを使う人へ、直近の具体的な中断事故を聞く必要があります。

「この製品を使いたいですか」と聞くのではありません。

最後に作業が止まったのはいつか。そのとき何をしたか。何分かかったか。何をやり直したか。どんなメモやツールを使ったか。

過去の行動を聞きます。

## 今回分かったこと

今回の実験で一番強く感じたのは、**AIにソフトを作らせることと、AIに価値を作らせることは別の仕事だ**ということです。

テストが通っても、利用者の問題は解決していません。

CLIが起動しても、欲しい判断材料が出なければ、ただの動く箱です。

AIは放っておくと、仕組みを増やす方向へ進みがちです。

自動化基盤、レビュー基盤、ループ、エージェント、さらにそれらを管理する仕組み。どれも役に立ちますが、目的を忘れると、料理を作らず厨房だけが豪華になります。

今回、追加課金3,000円は少々痛かったのですが、最後には具体的な製品仮説まで出せました。

次に作るべきものは、もう一つの巨大なAI基盤ではありません。

まずは、自分のCodex、Claude Code、Gemini CLI間で使える、小さなPortable Work Checkpointの試作品です。

それを自分で使い、実際に再説明や再実行が減るかを確かめます。

needs-detectorの本当の評価も、ここから始まります。
