## 必須修正1：project.yamlのFixture設定を本当に機能させる

現在の`MockLLMProvider._get_fixture_key()`では、`yaml`が未定義のまま使用され、例外が握りつぶされる可能性がある。

次を満たすこと。

- `yaml`を正しいスコープでimportする
- `except Exception: pass`で設定読み込み失敗を隠さない
- YAML構文エラー、型不正、未知のFixtureキーを明示的な例外として扱う
- Fixture選択の優先順位を明文化して実装する

推奨優先順位：

1. CLIの`--fixture-key`
2. `project.yaml`の`mock_fixture_key`
3. 環境変数`MOCK_FIXTURE_KEY`
4. 明示的な`default`

コンテキスト文字列の内容（`Persona A`等）を見てFixtureを暗黙選択する処理は削除する。

### 必須テスト

- `project.yaml`へ`mock_fixture_key: dataset_b`を設定し、CLI引数なしでDataset Bが選ばれる
- CLI引数がproject.yaml設定を上書きする
- 不正YAMLは明示的に失敗する
- 未知Fixtureキーは`MockFixtureNotFoundError`になる

## 必須修正2：Manual LLMジョブを一意に管理する

Manual LLMのプロンプトファイルを、固定名だけで保存してはならない。

### 必須仕様

各Manual要求に一意な`job_id`を発行し、少なくとも次を保存する。

```yaml
job_id: <一意ID>
prompt_used: draw_persona | explore_alternatives | interview_guide | learn_interview
target: <対象インタビューIDまたはnull>
status: waiting_llm | imported | failed
prompt_file: <相対パス>
response_file: <相対パスまたはnull>
created_at: <ISO日時>
imported_at: <ISO日時またはnull>
```

保存先の例：

```text
manual_jobs/<job_id>/request.json
manual_jobs/<job_id>/response.json
manual_jobs/index.yaml
```

設計上同等であれば別構成でもよい。

### 必須条件

- 複数インタビューの`learn --provider manual`で、各インタビューごとに別のジョブと別のプロンプトを生成する
- 後続ジョブが前のプロンプトを上書きしない
- `target`をレスポンスファイルの自己申告だけに依存せず、登録済みジョブ情報と照合する
- 同じジョブの二重インポートを拒否するか、明確な冪等動作にする
- 未登録の`job_id`、prompt不一致、target不一致はexit code 1

`import-llm-response`には、回答ファイル内またはCLI引数によって`job_id`を指定できるようにする。

## 必須修正3：全Manual回答が揃うまで完了扱いにしない

### Step 1 Draw

- プロンプト生成後：`step1_draw = waiting_llm`
- 対応する回答の取込成功後だけ：`step1_draw = completed`

### Step 2 Explore

- プロンプト生成後：`step2_explore = waiting_llm`
- 対応する回答の取込成功後だけ：`step2_explore = completed`

### Step 3 Interview Guide

- プロンプト生成後：`step3_listen = waiting_llm`
- 回答取込とguide生成後：`step3_listen = in_progress`

### Step 4 Learn

複数インタビューがある場合、すべての対象ジョブが`imported`になるまで、次を禁止する。

- `learn_results.yaml`の最終確定
- CPFの最終評価
- `step3_listen = completed`
- `step4_learn = completed`

一部だけ取り込んだ状態では、`step4_learn = waiting_llm`を維持し、未取込ジョブ数と対象を`status`で表示する。

### 必須テスト

インタビューを2件登録してManual Learnを実行し、次を確認する。

1. 2件の異なるジョブが生成される
2. 1件目を取り込んでもStep 4は`waiting_llm`
3. 2件目を取り込んだ後だけStep 3とStep 4が`completed`
4. CPFは2件分の証拠から集計される
5. 各引用が対応する原文・行番号と一致する

## 必須修正4：Manual 4工程の完全往復E2E

現在のテストは、プロンプト生成と一部の待機状態しか確認していない。次の完全E2Eテストを追加する。

```text
init
  ↓
add-idea / add-source
  ↓
draw --provider manual
  ↓
Draw回答をimport
  ↓
explore --provider manual
  ↓
Explore回答をimport
  ↓
interview-guide --provider manual
  ↓
Guide回答をimport
  ↓
インタビュー2件を登録
  ↓
learn --provider manual
  ↓
回答1件目をimport（まだwaiting_llm）
  ↓
回答2件目をimport（ここでcompleted）
  ↓
report
  ↓
status
```

各段階で、終了コード、状態、成果物の内容を確認する。単にコマンドが終了しただけでは合格にしない。

## 必須修正5：AI補完情報を実データとして追跡する

固定文の次のような表示は禁止する。

```text
AI補完部分: ペルソナとインタビュー事実との間の推論による補完
```

### 必須仕様

- LLMレスポンスの`ai_completions`を工程ごとに保存する
- Draw、Explore、Interview Guide、Learnのどの工程で生成された補完か識別できる
- 内容、工程、関連成果物、可能ならjob_idまたはfixture名を保存する
- Mock Fixtureにも意味のある`ai_completions`を持たせる
- Manual回答も`ai_completions`をPydanticで検証する
- レポートは保存済みの実データのみを列挙する
- 補完がない場合は`(AI補完なし)`と表示する

`ai_completions`がレスポンス本体の外側にある現在の形式を維持してもよいが、ManualとMockで同じ検証・保存経路を通すこと。

## 必須修正7：wheel配布物を実際に検証する

ソースツリーを`PYTHONPATH`へ直接追加するだけでは、wheel配布確認にならない。

### 必須試験

ネットワーク不要の方法で次を実行する。

1. wheelをビルドする
2. wheelをZIPとして検査し、`needs_detector/fixtures/llm/*.json`が含まれることを確認する
3. wheelを一時ディレクトリへ`pip install --no-deps --target <temp>`等で展開・インストールする
4. リポジトリ外をカレントディレクトリにする
5. ソースツリーの`src`を`PYTHONPATH`へ追加せず、インストール先だけを参照する
6. インストール済みパッケージから`MockLLMProvider`を起動し、Dataset A/BのFixtureを読み込めることを確認する
7. 可能ならインストール済みCLIで`init`と`draw --fixture-key dataset_a`を実行する

ビルドツールが環境にない場合、`pip wheel --no-deps .`など、現在の環境でネットワーク不要の代替方法を使う。単に「設定を確認した」だけでは合格にしない。

## その他の必須品質条件

- `open(... )`をコンテキストマネージャなしで多用しない

- 全テストをオフラインで実行可能にする
