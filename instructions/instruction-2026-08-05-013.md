# instruction-2026-08-05-013

## 目的

`needs-detector` を動作確認で終わらせず、現実の公開情報を入力して、利用者が読める具体的なニーズ探索結果を1件完成させる。

今回の調査テーマは次とする。

> AIコーディングCLIを複数併用する個人開発者・小規模開発者が、セッション制限、コンテキスト喪失、再開、複数AI間の引継ぎで直面する問題

このテーマは最初から正しいと仮定しない。公開GitHub Issueから観察可能な事実を集め、反証も含めて分析し、優先ニーズ、現在の代替手段、未確認事項、次に行うべき人間インタビューを成果物として出す。

対応結果は `result-2026-08-05-013.md` に記録する。

## 今回の「結果」の定義

単にコマンドが成功したことを結果としない。最低限、次を読める形で提示する。

1. 根拠付きの優先ニーズ上位3件以上
2. 各ニーズを支持する公開Issueと、反証・例外
3. 現在使われている回避策・代替手段
4. 最も有望な問題仮説1件
5. その問題を解く製品・機能仮説3案
6. 実顧客インタビューで確認すべき対象者、質問、合否基準
7. 現時点でCPFや市場成立を断定できない理由

最終成果物は `pilots/ai-coding-continuity-013/final-needs-report.md` とする。

## 重要な境界

- 公開GitHub Issueは現実に投稿された観察材料だが、今回の調査では「顧客インタビュー」とみなさない。
- `add-interview`へ登録する場合は、必ず `--data-classification unknown` とする。
- 実顧客検証済み、CPF確立、市場成立、購入意思確認済みなどと表示・記述しない。
- Issue投稿者の氏名、メールアドレス、組織名など、分析に不要な個人情報を保存しない。
- Issue本文を大量転載しない。1件につき短い引用は25語以内とし、残りは自分の言葉で要約する。
- 数値、日付、Issue番号、URL、反応数、コメント数を推測しない。取得できない項目は `unknown` とする。
- 外部情報へアクセスできない場合は、架空の資料で代用せず `BLOCKED` とする。

## Manual LLMによる実データ処理

Mock fixtureは使用しない。`--provider manual` を使用し、実際に収集した資料をもとに各工程を完了させる。

主担当AIは、CLIが出力する `manual_prompts/<job_id>/request.json` を読み、外部LLM役として応答JSONを作成し、`needs-detector import-llm-response` で取り込む。

応答作成時は次を守る。

- `job_id`、`prompt_used`、`target` をrequestと完全一致させる。
- `content` はCLIのPydantic schemaに一致するJSON objectとする。
- `ai_completions` には、AIが補完・推論した内容と関連成果物を記録する。
- 観察事実、引用、仮説、推論を混同しない。
- source_referenceにはIssue番号または登録資料名を入れる。
- 根拠のない人物像、企業規模、支払意思、頻度を作らない。

次の順で実行する。

```text
needs-detector draw --provider manual
needs-detector import-llm-response <draw response>

needs-detector explore --provider manual
needs-detector import-llm-response <explore response>

needs-detector interview-guide --provider manual
needs-detector import-llm-response <guide response>
```

## 公開Issue観察記録の登録

収集したIssueをテーマ別に6件以上の観察記録へ整理する。

例:

- セッション・利用量制限
- コンテキスト圧縮と情報欠落
- クラッシュ・再起動後の復旧
- 複数AI・サブエージェント間の状態共有
- 長時間タスクの進捗・チェックポイント
- 手作業の回避策と不満

各観察記録は、2件以上のIssueを横断して構成してよい。ただし、どの記述がどのIssueに由来するかを行単位で追跡できるようにする。

観察記録は次のような形式にする。

```text
# Public Issue Observation: <theme>

- Source: <repo>#<issue>
- Event: <具体的に起きたことの要約>
- Workaround: <実際の回避策。なければunknown>
- Impact: <時間、再作業、停止など。取得不能ならunknown>
- Short quote: <25語以内>
- Interpretation: <推論であることを明記>
```

これらはインタビューではないため、次で登録する。

```text
needs-detector add-interview <observation-file.md> --data-classification unknown
```

## Learnとレポート生成

すべての観察記録を登録後、Manual providerでLearnを実行する。

```text
needs-detector learn --provider manual
```

生成された全jobについて、requestの対象と原文行を確認して応答を作り、取り込む。

- 引用行番号はraw観察記録と完全一致させる。
- `cpf_evidence` は、公開Issueから確認できた事実だけを記載する。
- 支払額、利用頻度、組織内意思決定、継続利用理由など未確認のものは空またはunknownとする。
- 公開IssueだけでCPF成立としない。

全job取込後、次を実行する。

```text
needs-detector status
needs-detector doctor --json
needs-detector next --json
needs-detector report
```

生成されたレポートを確認し、CLI生成レポートの保存先と状態を記録する。

## 最終ニーズレポート

`pilots/ai-coding-continuity-013/final-needs-report.md` を作成する。

### 必須構成

1. Executive Summary
2. 調査対象と方法
3. 収集した証拠の内訳
4. 優先ニーズランキング
5. 最重要問題仮説
6. 現在の代替手段・回避策
7. 反証・すでに解決済みの事項
8. 製品・機能仮説3案

10. Go / Continue / Stop基準
11. 限界と未確認事項
12. needs-detectorが生成した成果物一覧

### ニーズランキング

最低3件のニーズを、次の5項目を各0〜5点で評価し、25点満点で順位付けする。

- 観察件数
- 複数リポジトリへの広がり
- 作業損失・停止の重大さ
- 手作業の回避策が存在する度合い
- 未解決または再発している度合い

点数はIssue件数から機械的に決めず、根拠と不確実性を書く。

各ニーズには最低2件のIssue参照を付ける。最重要問題仮説には、支持証拠、反証、未確認事項を併記する。

### 製品・機能仮説

3案は機能名だけでなく、次を含める。

- 誰のどの場面を助けるか
- 入力
- 出力
- 既存回避策との違い
- 最小実験
- 失敗判定

少なくとも1案は、既存のAI Director / orchestratorの考え方を応用した「作業状態と引継ぎの自動保存・復旧」とする。ただし、最有望と決めつけない。

### 実顧客インタビュー計画

次を出す。

- 対象者3類型以上
- 募集条件
- 最初の5人を見つける方法
- 過去の具体的行動を聞く質問10問以上
- 誘導質問になっていないことの確認
- 5件の面談後に継続・修正・中止を判断する基準

「使いたいですか」「買いますか」だけで判断しない。
