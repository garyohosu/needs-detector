## 今回の主要な是正対象

### 1. Draw処理

現在の固定値出力を廃止する。

`draw` は最低限、次を入力として読むこと。

- `idea.md`
- `sources/index.yaml`
- 登録済みの一次資料

出力する各ペルソナには最低限、次を持たせる。

- ID
- ペルソナ名または役割名
- 状況
- 機能的ジョブ
- 感情的ジョブ
- 社会的ジョブ
- 阻害要因
- 現在の対処方法
- 現在の対処方法への不満
- 根拠種別
- 出典参照
- AI補完部分
- 現実の顧客に確認すべき事項

同じコマンドでも入力資料が異なれば、出力内容が変わること。

### 2. Explore処理

固定の `Alt 1`, `Alt 2` を廃止する。

アイデア、ペルソナ、ジョブ、登録資料から次を分類して出力する。

- 直接競合
- 間接代替
- 無消費

各項目には最低限、次を含める。

- 名称または行動
- どのジョブを満たすか
- 利点
- 問題点
- 費用または時間
- 不満があっても使われる理由
- 根拠種別
- 出典
- 未確認事項

ネット検索は今回の必須要件にしない。登録された資料とMock出力だけで完全オフライン試験できるようにする。

### 3. LLMProvider

`MockLLMProvider` と `ManualLLMProvider` を実際のワークフローへ接続する。

#### MockLLMProvider

- 入力コンテキストを受け取る
- 入力に基づく決定的な構造化結果を返す
- テスト中に同じ入力なら同じ結果を返す
- 異なる資料なら異なる結果を返す
- ネットワークやAPIキーを使用しない

#### ManualLLMProvider

- `manual response` という固定文字列を返してはならない
- 実行時に、別AIへ投入できる完全なプロンプトをMarkdownまたはJSONで出力する
- プロンプトには、指示、入力資料、期待するJSONスキーマ、事実と仮説の区別を含める
- 出力先をユーザーへ表示する
- AI回答のインポート方法を用意する。最低限、所定のJSONファイルを読み込んで次工程に進めること

### 4. Interview Guide

固定の1問だけを出してはならない。

最低限、次の5問と、回答が浅い場合の掘り下げ質問を生成する。

1. 一番の難題
2. 最後に直面した具体的状況
3. なぜ大変だったか
4. 実際に取った行動
5. 現在の方法の不満

誘導質問検出を実際のガイド生成結果へ適用し、警告対象の質問が残っていないことをテストする。

### 5. Interview取込と匿名化候補検出

特定の氏名・会社名をハードコードしてはならない。

最低限、次を一般的なパターンとして検出する。

- メールアドレス
- 電話番号
- 郵便番号
- URL
- IPv4アドレス

日本語氏名、会社名、住所について、正規表現だけで高精度化できない場合は、確実にできる範囲を明記し、過剰な実装済み主張をしない。

検出結果は警告として保存し、元データを勝手に変更しない。

### 6. Learn処理

インタビュー記録の固定反証を廃止する。

実際の記録から最低限、次を抽出する。

- 具体的出来事
- 実際に取った行動
- 使用した時間・金額
- 現在の代替品
- 不満
- 当初仮説との一致
- 当初仮説との不一致
- 反証候補
- 引用と行番号

CPF評価は入力された証拠に基づくこと。

- インタビュー0件なら全項目 `未確認`
- 具体的出来事や行動がなければ `強い` にしない
- 時間・金額・代替品の証拠が増えると評価が変化する

### 7. Report処理

固定レポートを廃止する。

レポートはプロジェクト内の実データから生成し、最低限次を含める。

- 初期アイデア
- 対象ペルソナと状況
- 課題仮説
- 直接競合、間接代替、無消費
- インタビューから得た事実
- 反証
- CPF評価
- AI補完部分
- 未確認事項
- 次に確認すべきこと

事実、引用、仮説、推論、未確認を明確に表示し、引用には出典と行番号を付ける。

### 8. パス安全性

`atomic_write` という名前だけで安全と判定してはならない。

- 書込み対象がプロジェクトルート配下であることを検証する
- `..`、絶対パス、シンボリックリンク等によるルート外書込みを拒否する
- コピー処理も対象とする
- 違反時は専用例外を送出する
- 既存ファイルを壊さないアトミック書込みを維持する

## テストの全面見直し

### 実CLIのE2Eテスト

内部サービスを直接呼ぶだけではE2Eと呼ばない。

少なくとも次のいずれかで、インストール後の実CLIを実行する。

```bash
python -m needs_detector.cli.main ...
```

または

```bash
needs-detector ...
```

`subprocess`等を使い、次を確認する。

- 終了コード
- 標準出力・標準エラー
- 実際の生成ファイル
- 不正入力時の失敗
- 人間確認ゲート

### 入力差分テスト

異なる2種類以上の資料セットを用意し、次を確認する。

- ペルソナが異なる
- ジョブが異なる
- 代替品が異なる
- 最終レポートが異なる

固定値実装なら失敗するテストにする。

### 反証テスト

仮説を支持するインタビューと、否定するインタビューを別々に用意する。

- 支持発言を反証として扱わない
- 否定発言を反証候補として抽出する
- 引用行番号が元記録と一致する

### パス安全性テスト

次を実際に拒否することを確認する。

- `../outside.txt`
- プロジェクト外の絶対パス
- ルート外を指すシンボリックリンク。OS上で作成不能な場合は理由を記録する

### 秘密情報・Git除外テスト

特定PCの `C:/PROJECT/...` を参照しない。
リポジトリルートを動的に特定し、`.gitignore` の必須項目を必ず検査する。
ファイルが見つからなければスキップせず失敗させる。

### Windows互換性テスト

`Path("C:\\...").is_absolute()` だけで合格にしない。
最低限、次を確認する。

- UTF-8日本語ファイル名の入出力
- スペースを含むパス
- `pathlib`による区切り文字処理
- Windows専用試験が非Windows環境で実行不能な場合は、明示的にskip理由を記録する

### テスト品質規則

次のテストは禁止する。

- `assert True`
- 実装関数を一度も呼ばないテスト
- ファイルが存在しない場合に何も確認せず通過する条件分岐
- 固定出力と同じ固定文字列を比較するだけで、入力依存性を検証しないテスト

Agent Aはテストコードそのものを読み、偽テストや弱いテストがないことを判定する。

## 自律レビュー

- Cycle 1: 実装修正後の初回審査

- Cycle 3: 2回目の指摘修正後の最終審査

Cycle 3で `PASS` にならなければ、Cycle 4へ進まず `BLOCKED` とする。

記録ファイルは次の形式とする。

```text

```

使用しなかったサイクルのファイルは作らない。
