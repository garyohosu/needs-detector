## 今回確認済みの問題

次の問題を「未確認事項」ではなく、修正必須の既知問題として扱う。

1. `MockLLMProvider` が `Path(os.getcwd()) / "tests" / "fixtures" / "llm"` を参照しているため、顧客プロジェクト内で実行すると Fixture を発見できない。
2. Fixture がない場合に固定ペルソナ、空の代替品、固定質問、固定反証を返すハードコードフォールバックが残っている。
3. 現在のE2Eテストは、その固定フォールバックと都合よく一致するインタビュー本文によって成功している。
4. `import-llm-response` の `interview_guide` と `learn_refutations` / `learn_interview` は、表示だけで成果物へ反映していない。
5. `learn --provider manual` は回答未取込でもCPF評価とStep 3 / Step 4完了処理へ進む。
6. 最終レポートは15個の見出しを作るだけで、実データを入れているのは実質Section 1だけである。
7. Manualインポート経路でPydanticスキーマ検証を行っていない。
8. CLIの `interview-guide` に `--provider` がない。
9. CPFは三変数に分離されたが、反証がない場合に本文の証拠を評価できず、単語出現だけで過大評価される。

これらが一つでも残っている場合、Agent Aは `PASS` を出してはならない。

## Agent B: 実装担当の作業

### 1. Fixtureをパッケージリソース化する

Mock用Fixtureを、カレントディレクトリやテストディレクトリに依存せず、インストール済みパッケージから取得できる構成へ変更する。

推奨構成例:

```text
src/needs_detector/fixtures/llm/
├─ dataset_a_draw_persona.json
├─ dataset_a_explore_alternatives.json
├─ dataset_b_draw_persona.json
├─ dataset_b_explore_alternatives.json
├─ default_interview_guide.json
├─ learn_interview_with_refutation.json
└─ learn_interview_without_refutation.json
```

- `importlib.resources` などを使い、実行場所に依存せず読み込むこと。
- `pyproject.toml` でJSONリソースがwheelへ含まれることを確認すること。
- `pip install -e .` 後とwheelインストール後の両方で読み込める設計にすること。
- `tests/fixtures` を実行時リソースとして直接参照してはならない。

### 2. 固定フォールバックを完全削除する

次のようなコード内固定レスポンスをすべて削除する。

- 固定Persona
- 固定Job
- 空のalternatives
- `Q1` / `D1`
- `I didn't use it`
- `interview_fake`
- 固定行番号
- `mock_hash`

必要なFixtureがない場合は、明示的な例外を送出する。

例:

```text
MockFixtureNotFoundError
```

存在しないFixtureを固定レスポンスでごまかしてはならない。

### 3. Fixture選択を明示的にする

入力文中の偶然の文字列やPersona名を使った暗黙判定だけに依存しない。

次のいずれかを実装する。

- `--fixture-key dataset_a`
- プロジェクト設定 `mock_fixture_key`
- テスト時に注入可能なFixtureResolver

通常利用で `mock` を選択した場合、どのFixtureを使ったかを監査ログへ記録する。

### 4. Manual LLMの完全往復

次の4工程すべてについて、プロンプト出力、回答インポート、スキーマ検証、成果物保存、状態更新まで実装する。

```text
draw_persona
explore_alternatives
interview_guide
learn_interview または learn_refutations
```

#### interview_guideインポート

- `InterviewGuideResponse` で検証
- `QuestionChecker` を全質問へ適用
- `interviews/guide.md` を作成
- Step 3を `in_progress` に更新

#### learnインポート

- 対象インタビューを一意に特定できる情報をプロンプトと回答へ含める
- `InterviewAnalysisResponse` で検証
- 引用と原文行番号を再検証
- 対応するインタビューYAMLへ分析結果を書き込む
- 全対象インタビューの回答取込完了後にのみCPF評価とStep 3 / Step 4完了処理を行う

### 5. Manual待機状態を実装する

`draw --provider manual`、`explore --provider manual`、`interview-guide --provider manual`、`learn --provider manual` は、プロンプトを書き出した時点で完了扱いにしない。

`project.yaml`の状態例:

```yaml
status:
  step1_draw: waiting_llm
  step2_explore: waiting_llm
  step3_listen: waiting_llm
  step4_learn: waiting_llm
```

- 回答インポート後に次の正しい状態へ進める。
- 回答未取込で `report` を実行した場合は、未確認と待機中を区別して表示する。

### 6. CLIを修正する

最低限次を実装する。

```text
needs-detector interview-guide --provider mock|manual
needs-detector draw --provider mock|manual --fixture-key <key>
needs-detector explore --provider mock|manual --fixture-key <key>
needs-detector learn --provider mock|manual --fixture-key <key>
needs-detector import-llm-response <file>
```

引数設計は整理してよいが、4工程すべてでMockとManualを選択できること。

### 7. Manual回答も必ずスキーマ検証する

Manual回答を読み込んだ後、対応するPydanticモデルで検証してから保存する。

- JSON破損
- 必須フィールド不足
- 不正な`evidence_type`
- 不正な行番号型
- 不明な`prompt_used`
- 対象インタビュー不明

は、明確な例外と非ゼロ終了コードにする。

### 8. 15セクションレポートへ実データを反映する

単なる `Section 1` 〜 `Section 15` という見出し名ではなく、意味のある日本語または英語の見出しを付ける。

最低限、次を含める。

1. 初期アイデア
2. 入力資料と出典
3. 対象ペルソナ
4. ペルソナが置かれた状況
5. 機能的ジョブ
6. 感情的ジョブ
7. 社会的ジョブ
8. 阻害要因
9. 現在の対処方法と不満
10. 直接競合
11. 間接代替
12. 無消費
13. インタビューから得た事実と引用
14. 反証、CPF評価、AI補完部分
15. 未確認事項と次に確認すべきこと

- 対応する成果物が存在する場合、`未確認`のままにしてはならない。
- 引用には実際のファイル名と行番号を付ける。
- AI補完部分と事実を区別する。
- レポート内容が入力差分によって意味的に変化するテストを作る。

### 9. CPF評価を証拠ベースへ改善する

三軸を独立評価することに加えて、単純な全文キーワード検索だけに依存しない。

推奨する入力構造:

```yaml
cpf_evidence:
  real_problem:
    concrete_events: []
    frequency: []
    impact: []
  first_mover:
    time_spent: []
    money_spent: []
    attempts: []
  current_alternative:
    alternatives_used: []
    dissatisfaction: []
    continued_use_reason: []
```

- `未確認`、`弱い`、`一部確認`、`強い`の条件をコード上で明示する。
- 反証が0件でも、肯定的な具体証拠を評価できること。
- 一つの同じ単語だけで三軸すべてが強くならないこと。
