ただし、製品機能として設計されている顧客インタビュー、人間確認ゲート、未検証表示は削除しない。今回なくすのは、開発工程における逐次的な人間承認待ちである。

`result-2026-08-05-004.md`

## 自律実行方針

作業を次の二役に分ける。

### Agent B: 実装・テスト担当

Agent Bは、設計書とテスト計画に従ってコード、テスト、設定、ドキュメントを作成・修正する。

### Agent A: 独立審査担当

Agent Aは、実装コードを変更してはならない。次のみを入力として審査する。

- `memo.md`
- `DESIGN.md`
- `TESTPLAN.md`
- 今回のGit差分
- テスト実行結果
- Agent Bの開発記録

審査結果は、各サイクルごとに次のファイルへ記録する。

```text
records/agent-a-review-004-cycle-1.md
records/agent-a-review-004-cycle-2.md
records/agent-a-review-004-cycle-3.md
```

判定は次のいずれかとする。

- `PASS`: 要求と受け入れ条件を満たす
- `REVISE`: 修正可能な不足がある
- `BLOCKED`: 人間にしか解決できない停止条件がある

`REVISE` の場合、Agent Bへ戻して修正、再テスト、再審査を行う。最大3サイクルまで自動反復する。途中で人間の確認を求めない。

サブエージェントが利用可能ならAgent AとAgent Bを別サブエージェントにする。利用できない場合は、同一実行内でも役割と出力を厳密に分離する。

## 実装範囲

Python 3.12以上で動作するローカルCLIのMVPを実装する。

最低限、次を作成する。

```text
pyproject.toml
src/needs_detector/
tests/
.gitignore
README.md
records/agent-b-implementation.md
```

`DESIGN.md` のレイヤー構造を基本とし、必要に応じて実装可能な最小構成へ整理してよい。ただし、要求仕様を削ってはならない。

### 必須CLI

次のコマンドを実装する。

```text
needs-detector init
needs-detector add-idea
needs-detector add-source
needs-detector draw
needs-detector explore
needs-detector interview-guide
needs-detector add-interview
needs-detector learn
needs-detector report
needs-detector status
```

### LLM機能

- 初期版は外部APIなしで動作させる
- `MockLLMProvider` を必須とする
- 手動投入用のプロンプトをファイル出力できる `ManualLLMProvider` を実装する
- OpenAI、GeminiなどのAPIキーを要求しない
- 実APIアダプターは今回の必須範囲外とする

### 必須ドメイン機能

- 根拠種別 `evidence`, `quote`, `hypothesis`, `inference`, `unknown`
- 出典メタデータ保存
- 誘導質問の検出と修正案
- インタビュー未登録時の人間確認ゲート
- 反証の優先抽出
- CPFの3軸評価
- 匿名化候補の検出
- 監査ログ
- パス外書き込みの防止
- UTF-8とWindowsパスへの配慮

## テスト

`TESTPLAN.md` の AC-001 から AC-012 を対象とする。

外部API、ネットワーク、秘密情報に依存せず、最低限次を実行する。

```bash
python -m pip install -e .[dev]
python -m pytest tests/ -v
```

カバレッジ設定が実装済みなら、次も実行する。

```bash
python -m pytest tests/ -v --cov=src/needs_detector
```

OSや環境の制約で一部を実行できない場合は、理由と代替確認方法を記録する。テスト失敗を残したまま `PASS` にしてはならない。

- 実装方針

- 作成・変更ファイル

## 審査基準

Agent Aは最低限、次を確認する。

1. `memo.md` の要求を満たしているか
2. AC-001〜AC-012のテストが存在するか
3. オフラインで全テストが成功するか
4. AI生成の内容を事実として扱っていないか
5. 顧客インタビューなしで検証済みにならないか
6. 誘導質問警告が機能するか
7. 反証と出典追跡が失われていないか
8. プロジェクト外へ書き込めないか
9. 秘密情報や顧客データがGit対象になっていないか
10. Agent AとAgent Bの記録が分離されているか

## 停止条件

次の場合だけ `BLOCKED` として停止する。

- `memo.md`、`DESIGN.md`、`TESTPLAN.md` が相互に矛盾し、安全に解釈できない
- 認証情報、秘密情報、有料API、外部サービスへの実アクセスが必要
- 破壊的なGit操作や既存データ削除が必要
- 法務、個人情報、製品方針についてユーザー固有の判断が不可欠
- 未コミット変更または競合により安全に作業できない
- 3回の修正サイクル後も審査が `PASS` にならない

パッケージ内部構造、関数名、テスト用サンプル、実装順序などの通常の技術判断では停止しない。

## 完了処理

最終審査が `PASS` になったら、次を行う。

1. `DESIGN.md` と `TESTPLAN.md` の状態を「MVP実装済み・審査PASS」に更新する
2. `result-2026-08-05-004.md` を作成する
3. 結果ファイルに次を記録する
   - 状態
   - 実施内容
   - 作成・変更ファイル
   - 全テストコマンドと結果
   - 審査サイクル数
   - 最終判定
   - 未解決事項
   - commitとpush結果
4. `git status --short` と `git diff` を確認する
5. 今回の作業に必要なファイルだけをコミットする
6. `git push origin main` を実行する

pushが成功した場合のみ `COMPLETED` とする。
