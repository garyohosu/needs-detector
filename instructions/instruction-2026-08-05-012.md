# instruction-2026-08-05-012

## 目的

`instruction-2026-08-05-011` まで完了した `needs-detector` を、開発者向けの単体テストではなく、初めて使う利用者の立場で実際にインストールして操作する。

インストール、プロジェクト作成、合成デモ、Manual LLM待機、Human Gate、診断コマンド、生成物を一連の流れとして確認し、CLIが実運用の入口として成立しているかを評価する。

対応結果はリポジトリ直下の `result-2026-08-05-012.md` に記録する。

## 実行方針

- この指示は1つのAI・1セッションで実行し、別エージェントや人間の途中承認を前提にしない。
- 最初はブラックボックス試験として実施し、ソースコードを読んで期待結果を合わせにいかない。
- 外部LLM APIは使用しない。MockとManual providerだけを使用する。
- 実在する個人名、会社名、メールアドレス、電話番号、顧客情報を入力しない。試験データはすべて合成データとする。
- 実験用プロジェクト、venv、wheel、ログはリポジトリ外の一時ディレクトリへ作成する。
- 大量の標準出力や一時生成物はcommitせず、必要な証拠だけをMarkdownへ要約する。

## 事前確認

1. `git status --short` を確認する。
2. `git pull --ff-only origin main` を実行する。
3. `origin/main` と同期した `main` であることを確認する。
4. 未追跡ファイルや別リポジトリが存在する場合は、削除、移動、stash、上書きを行わず、`origin/main` から専用cloneを作って実験する。
5. Python 3.12環境を使用する。実際に使用したPythonの完全なバージョンを記録する。

## 実験1: wheelを利用者環境へインストールする

リポジトリ外に空の作業ディレクトリとvenvを作成し、現在の `main` からwheelを作成してインストールする。

最低限、次を確認する。

- wheel作成が成功する。
- 新規venvへwheelだけをインストールできる。
- リポジトリをカレントディレクトリにせず `needs-detector --help` が成功する。
- helpにREADME記載の主要コマンドが表示される。
- インストール先がリポジトリ内の `src` を参照していないことを確認する。

実行したコマンド、終了コード、wheel名、venvの場所を記録する。

## 実験2: 最短の合成デモを最後まで操作する

インストール済みCLIだけを使い、リポジトリ外でREADMEの合成デモを実行する。

```text
needs-detector init synthetic-demo-012
cd synthetic-demo-012
needs-detector draw --provider mock --fixture-key dataset_a
needs-detector explore --provider mock --fixture-key dataset_a
needs-detector interview-guide --provider mock
needs-detector status
needs-detector doctor --json
needs-detector next --json
```

次を確認する。

- 初期化直後から各コマンドを迷わず順番に実行できる。
- 各工程の終了コードと表示内容が、現在の状態と矛盾しない。
- `status` が完了工程、未完了工程、データ区分を誤認させない。
- `doctor --json` と `next --json` が正しいJSONとして解析できる。
- `doctor` のerrors、warnings、next_actionsが利用者の次の行動に結び付く。
- personas、alternatives、interview guide、project stateなど、READMEから期待される生成物が存在する。
- 合成データを実顧客検証済み、CPF確立、市場成立と誤表示しない。

生成ファイルを全部貼り付けず、主要ファイル名、件数、重要な状態だけを記録する。

## 実験3: Human Gateを実際に止める

実インタビューを1件も登録していない合成デモの状態で、次を実行する。

```text
needs-detector learn --provider mock
```

次を確認する。

- `learn` が実顧客検証済みとして完了しない。
- 停止理由が利用者に理解できる。
- 終了コード、標準出力または標準エラー、実行後の `status` が相互に矛盾しない。
- 失敗後もプロジェクト状態や既存生成物が破損しない。
- `doctor --json` と `next --json` が、停止後の正しい次操作を示す。

Human Gateが単に例外終了するだけでなく、利用者を安全な次の行動へ案内できるかを評価する。

## 実験4: Manual LLM待機フローを操作する

別の新規プロジェクトを作成し、Manual providerで最初の要求を発行する。

```text
needs-detector init manual-demo-012
cd manual-demo-012
needs-detector draw --provider manual
needs-detector status
needs-detector doctor --json
needs-detector next --json
```

次を確認する。

- `manual_prompts/index.yaml` が作成される。
- `manual_prompts/<job_id>/request.json` が作成される。
- job_id、対象工程、必要な応答形式が利用者に追跡可能である。
- 状態が `waiting_llm` 相当として表示され、完了扱いにならない。
- `doctor` と `next` が、外部LLMへ渡す要求と回答取込の次手順を案内する。
- Manual待機中でも壊れた状態や実顧客検証済み表示にならない。

外部LLMへ実際に送信する必要はない。要求ファイルの内容と案内の分かりやすさを確認する。

## 実験5: 利用者視点の評価

次の観点を、事実と所感を分けて記録する。

- 初回利用者がREADMEだけで開始できるか。
- コマンド名、出力、生成ディレクトリが理解しやすいか。
- エラー時に何を直せばよいか分かるか。
- 合成データ、実データ、未分類データの違いを誤解しにくいか。
- AIの仮説と顧客事実を混同させない表示になっているか。
- 実際の顧客インタビューへ進む前に不足している説明がないか。

重大度は次で分類する。

- `BLOCKER`: READMEどおりに起動または主要フローを続行できない。
- `MAJOR`: 状態や安全性を誤認させる、データ破損、再現性のある重大な矛盾がある。
- `MINOR`: 操作は可能だが案内、文言、生成物の分かりにくさがある。
- `OBSERVATION`: 不具合ではない改善候補。

## 不具合を発見した場合

- まず再現手順、期待結果、実際結果、終了コード、環境を `records/operation-experiment-012.md` に記録する。
- `BLOCKER` または `MAJOR` の再現可能な不具合だけは、この指示内で最小修正してよい。
- 修正する場合は回帰テストを追加し、全テスト、カバレッジ、wheel packaging、該当する実操作を再実行する。
- 新機能追加、大規模リファクタリング、無関係な文言修正は行わない。
- `MINOR` と `OBSERVATION` は原則として修正せず、次回候補として記録する。
